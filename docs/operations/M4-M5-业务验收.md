# M4/M5 业务工作台、API 与本机验收

已交付库内关联、反馈指导与修订发布工作台及后台API，沿用原生登录、KB读写权限和本机Host。原生生命周期页继续可用。

## 页面使用

登录后从左侧导航进入，或访问当前前端地址下的路径：

| 页面 | 路径 | 验收操作 |
|---|---|---|
| 文档关联 | `/platform/associations` | 选择KB与两篇生效文档；保存相关候选，刷新后仍可查看/确认，查询有效关联，随后撤销。补充依赖继续在生命周期页维护。 |
| 反馈与指导 | `/platform/feedback-governance` | 录入反馈并查看完整内容；中/高风险人工批准后等待冷静期，高风险激活需再次确认；指导清单可录入种子或转入修订。 |
| 修订发布 | `/platform/revisions` | 选择源文档与1–3条生效指导，填写完整Markdown；审批后核对并发布，详情查看状态和新文档ID。 |

只读用户可查询和查看完整详情，不显示写入入口；服务端仍独立校验权限与revision。所有列表每页20项。记录状态冲突时重新载入详情再决定；网络/503结果未知时用“刷新核对”或“重试原请求”，页面保留原操作编号和原内容。核对结束前不能切页/切库，确认已核对后才选择“结束重试”。刷新整个浏览器会提示离开，不能代替持久业务查询。

当前反馈为管理录入，不是问答页点赞采集；指导尚未注入问答。文件类源可创建修订建议，自动正式发布仍仅支持在线Markdown。

## 启动

WSL 仓库根目录：

```bash
cd /mnt/d/LanRAG-Next
mkdir -p tmp
CGO_ENABLED=1 go build -mod=readonly -tags=lite,sqlite_fts5 -o tmp/WeKnora-lite-business-check ./cmd/server
CORE_BINARY="$PWD/tmp/WeKnora-lite-business-check" bash start-all.sh
```

复用已有私有启动配置。Host仍须`AGENTRAG_MODE=worker`、独立`AGENTRAG_EXT_DB`、租户/KB范围及上游API凭据；Core/Host的`AGENTRAG_MANAGEMENT_KEY`一致，一键启动器会处理。Host自动升级独立扩展库至schema11，原生weknora.db不做新迁移；不要手工重复执行SQL，也不需要reset。正常停机后再启动新版本，不要并行运行两个Host。

前端开发服务使用当前源码（Windows或WSL中选一种运行）：

```bash
cd frontend
npm run dev -- --host 127.0.0.1 --port 18880
```

从启动日志确认实际地址，登录同一Core后打开上述页面。现有开发代理配置仍沿用项目配置。生产静态部署需在`frontend/`执行`npm run type-check`、`npm run build`，再按现有静态部署方式更新`dist/`；上面的纯Go构建不会自动把新前端嵌入Lite二进制。本批未执行`make build-lite`、替换静态目录或重启用户服务。

真实发布凭据需要目标KB的`retrieve`和`ingest`能力。未经新版本重启，旧Core没有下面的新路由。

## 接口与权限

路径统一为`/api/v1/knowledge-bases/{kb_id}/lifecycle/business/{action}`。使用原生登录JWT；API Key不能调用管理接口。Host密钥只留在服务端。

- GET只读：`related?document_id=...`、`relation_list`、`feedback_list`、`guidance_list`、`revision_list`。
- 列表支持`?id=...`精确查看和`?page=1&page_size=20`分页，page_size最多20；返回正文、风险/冷静期或完整修订内容供审批。
- PUT写入：下面表中的动作，需要库owner/admin或共享库editor及原生Contributor权限。tenant、actor、can_write由服务端决定，不能放到浏览器请求体。

统一写入请求：

```json
{
  "operation_id": "每次新操作使用一个新ID；同操作重试沿用原ID和原请求",
  "expected_revision": 0,
  "business": {"id": "更新对象时填写，创建时省略", "payload": {}}
}
```

返回`data.id/revision/status`；更新时带回当前revision。409表示状态/版本冲突或冷静期/主题熔断尚未满足，先读取再决定；不要用新operation_id绕过未知发布结果。

| action | payload / 作用 |
|---|---|
| `relation_declare` | `document_id`,`target_document_id`,`edge_type`=`amends`/`interprets`/`related_to`；同库。前两者显式声明后active；related_to先candidate |
| `relation_confirm` / `relation_revoke` | `business.id`与expected_revision；确认语义候选或撤销关系 |
| `feedback_create` | `text`,`topic`,`risk`=`low`/`medium`/`high`，可带`negative:true`；当前为管理录入，不冒充真实问答反馈采集 |
| `feedback_approve` / `feedback_reject` | 审批pending_review；low自动批准并等待24h，medium人工批准后48h，high人工批准后72h |
| `feedback_activate` | 冷静期满足后激活；high还需`second_confirmation:true`。本批显式调用激活，未挂自动激活扫描 |
| `feedback_quarantine` / `feedback_withdraw` | 隔离或撤回，同时停用对应指导 |
| `guidance_seed` | `text`,`topic`；source=seed、confidence=0.75；建议初始手工录入3–5条。同主题已有两次负反馈时，新种子也会隔离 |
| `guidance_quarantine_topic` | `topic`；同主题负反馈达到2次才能隔离，反馈录入达到阈值时也自动执行 |
| `revision_create` | `document_id`,`guidance_ids`（1–3个active指导ID）,`text`（完整新Markdown，最多48000字节，**不是补丁diff**） |
| `revision_approve` / `revision_reject` | 审批pending_review提案；不修改原文 |
| `revision_publish` | `business.id`；持久发布意向→先远端对账→仅确认不存在才创建→索引→原子finalize |

`related`双向返回关系，`direction=incoming/outgoing`保留方向语义；仅当前active、版本匹配的文档，包含已生效T3 supplements。related_to低于0.7不返回；默认权重0.60/0.25/0.15分别用于similarity/declaration/structure，尚未用真实标注校准。supplements声明继续使用原生命周期文档的`/supplements`接口，不能借普通关系接口绕过T3依赖规则。

### 一个请求示例

```bash
export CORE_URL=http://127.0.0.1:8080
export KB_ID=你的知识库ID
read -rsp '原生登录 JWT: ' CORE_TOKEN
curl --fail-with-body "$CORE_URL/api/v1/knowledge-bases/$KB_ID/lifecycle/business/guidance_seed" \
  -X PUT -H "Authorization: Bearer $CORE_TOKEN" -H 'Content-Type: application/json' \
  --data '{"operation_id":"seed-effective-date-1","expected_revision":0,"business":{"payload":{"text":"回答条款问题时核对文档有效期。","topic":"effective-date"}}}'
```

## 发布行为与恢复

仅原生`manual`且已publish的Markdown源可自动发布新文档。原生PDF/DOCX/其他文件可以创建建议、审批，但自动发布会记录`binary_source_upload_required`；正式文件必须走后续“用户上传修订文件→绑定提案”流程。

发布使用稳定publication_key和确定性标题`AgentRAG revision <key>`；对账验证租户、KB、完整分页、标题、原生metadata中的实际Markdown hash。分页不完整/远端未知都不能当作不存在。单个提案通过扩展持久lease/CAS串行发布，超时不重新执行原生创建。

远端已提交但应答丢失时，重新调用`revision_publish`进行对账；不要手工再次上传同一修订。若返回409且仍publishing，等待当前最长2分钟lease结束后再继续。列表中`publish_error`提供安全错误码；已创建目标会保留target_document_id，查不到目标时也不会直接再建。

只有finalize提交后才返回published：新→旧supersedes边、旧文档active→superseded事件/current、生命周期与family投影意向、提案状态和业务审计/回执处于同一个扩展事务。原生旧文档原件保留，但M2检索策略排除它。审计失败时这些最终事实整体回滚，已创建远端目标通过下次reconcile找回。

family_id在修订链中继承；M3观察版本族仍按原生document_id登记，不重写已观察的family/current。`family_tag`意向已入Outbox，处理器与真实family标签投影尚待接线，可能进入重试/dead；这不改变治理truth，也不宣称标签同步成功。原有C-10未知tags拒绝继续保留。

## 自动验证

8090空闲时，在WSL仓库根运行：

```bash
CORE_BINARY="$PWD/tmp/WeKnora-lite-business-check" \
AGENTRAG_BUSINESS_E2E=1 \
AGENTRAG_GOVERNANCE_REPORT="$PWD/docs/evidence/m4-m5-business-e2e-2026-11-02.log" \
python3 extensions/scripts/governance_e2e.py
```

若生产Host占用8090，使用独立网络空间，不停止现有服务：

```bash
unshare -Urn -- bash <<'E2E'
set -e
ip link set lo up
export PATH=/usr/local/go/bin:$PATH
CORE_BINARY="$PWD/tmp/WeKnora-lite-business-check" \
AGENTRAG_BUSINESS_E2E=1 \
AGENTRAG_GOVERNANCE_REPORT="$PWD/docs/evidence/m4-m5-business-e2e-2026-11-02.log" \
python3 extensions/scripts/governance_e2e.py
E2E
```

脚本创建临时账号/KB与独立SQLite，使用真实候选Core和worker Host、确定性本机模型；先验证立即激活409，然后仅在临时测试库推进截止时间，验证真实反馈激活→指导→审批提案→原生Markdown上传/索引→supersedes→关联查询/撤销。随后继续原有RAG/Agent active/stale/断Host回归。**没有声称真实等待48h、调用云模型或修改用户数据。**
