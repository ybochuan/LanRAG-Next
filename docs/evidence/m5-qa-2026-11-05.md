## 真实 Core/Host 治理 E2E

E2E 自建临时目录与独立 SQLite（`tmp/governance-e2e-*`），使用本地模型夹具，不触碰用户库与生产服务。

前置：Core 二进制必须带 `sqlite_fts5` 构建标签，否则 Agent 检索会因缺少 `lite_embeddings_fts` 表整条失败（本轮首次运行即因此失败，见下节）。

```bash
cd extensions/scripts
CGO_ENABLED=1 /usr/local/go/bin/go build -tags=sqlite_fts5 -mod=readonly \
  -o "$(git rev-parse --show-toplevel)/tmp/governance-WeKnora-lite" \
  "$(git rev-parse --show-toplevel)/cmd/server"

AGENTRAG_QA_FEEDBACK_E2E=1 \
AGENTRAG_GUIDANCE_E2E=1 \
AGENTRAG_GOVERNANCE_REPORT=<report path> \
python3 governance_e2e.py
```

环境：Ubuntu 26.04 WSL2、Go 1.26.0 linux/amd64、gcc 15.2.0、Python 3.14.4。

## 本轮踩到并已定性的三个环境问题

**1. Core 必须带 `sqlite_fts5` 标签构建。** 第一次 E2E 失败于 `[RESULT] FAIL: active Agent search positive control failed`，SSE 里的真实原因是：

```text
Knowledge search failed: FTS5 query failed: no such table: lite_embeddings_fts
```

不带标签构建时 FTS 表不存在，Agent 的 `search_knowledge` 整条失败。加 `-tags=sqlite_fts5` 重编后同一命令全绿。这不是代码缺陷，但**任何验收构建都必须带该标签**，否则会把「构建参数错误」误读成「检索被治理拦截」。

**2. Clash fake-ip 会把域名解析成 `198.18.0.0/15`，被原生 SSRF 策略正确拒绝。** 表现为 `resolves to restricted IP 198.18.x: restricted range 198.18.0.0/15`。已在 Clash 订阅的 Merge 叠加层为测试域名加 `fake-ip-filter` 与 `nameserver-policy`，既未全局关闭 fake-ip，也未放宽 SSRF。详见 `PROJECT_CONTEXT.md` 对应条目。

**3. 前端 `mcpProxy.test.ts` 因 Windows 端口保留失败。** `listen EACCES: permission denied 127.0.0.1:5173`；Windows 保留了 `5170–5269` 段（`netsh int ipv4 show excludedportrange protocol=tcp`）。直接绑定实验证实 `5173/5174/5269 → EACCES` 而 `5270/8199 → OK`。该测试文件与 `vite.config.ts` 自 `d1c62cd` 起未改动，与本批无关；释放需管理员执行 `net stop winnat && net start winnat`。
