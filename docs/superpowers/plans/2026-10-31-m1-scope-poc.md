# M1-01 V1兼容与显式作用域 POC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** 在不修改核心的前提下，验证MinerU4.0.1原生V1请求形状经过独立代理后仍能上传、运行单job、取回ZIP，并隔离预配置scope。

**Architecture:** 沿用已确认的endpoint代理方案；`/parser/scopes/{route}/v1`由服务端静态绑定tenant/KB及独立凭据。代理仅作为可测试构造器，本批不挂生产Host。只支持原生单文件/file_id/ZIP子集，状态在进程内；生产持久化/预检/自动原生身份传输后续。

**Tech Stack:** 扩展Go1.26与标准库；Python标准库启动用户已有D:/mineru-venv的4.0.1（Flash、无模型预加载）。

**Spec:** Frozen第7节；M1 Source Map的M1-01、C-04/C-12/C-13；用户本轮授权继续下一步。

## Global Constraints

- 基点fa6353e；沿用当前codex/m1-parser-routing分支。核心、Frozen、BASELINE、module依赖及venv不修改，不自动提交/推送。
- 此处scope来自可信配置与调用方凭据，不代表已验证原生KB权限或文档归属；不以文件名/hash猜测KB。普通UI自动绑定仍未实现。
- upstream/public origin只接受显式IPv4回环HTTP；不跟随重定向、不用环境代理、不转发调用方凭据至后端、不回显后端错误body。
- 原生client可接pending→PUT→complete；代理为每次提交生成本地upload句柄，即使后端缓存completed也要求源字节证明，避免缓存绕过未来预检。
- 同scope同job请求在当前进程去重；远端结果未知不盲目重发。内存状态与不自动过期的有限容量只适用于POC，不承诺重启后的exactly-once。
- 默认JSON64KiB、源文件50MiB、结果64MiB；单scope最多128个上传及128个job记录。达到限额拒绝，不截断。
- 实测只用私有合成PDF与现有Flash能力，不启用GPU、不下载模型、不触碰用户原件/真实数据库。API服务临时回环端口及数据由脚本拥有并清理。

## Review Focus

- 冷/热源缓存都必须经过当前scope的字节与SHA256验证；不能仅用已知hash引用别人的输入。
- upload/file/job句柄不能跨scope使用；未知scope/坏凭据拒绝且无后端副作用。
- upload_url固定从配置origin生成，不能信任Host头或接受后端跨origin上传链接。
- 并发重复job和丢响应后的重复调用不应再次POST；此保证限当前进程，不外推重启。
- 超限/坏SHA/坏响应/取消/重定向必须明确失败，不能静默放行或泄露凭据/文档。
