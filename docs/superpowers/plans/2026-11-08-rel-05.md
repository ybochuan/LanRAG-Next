# REL-05 制度拆分发布实施计划

> **For agentic workers:** Use the executing-plans workflow. Each implementation task has a focused regression check.

**目标**：整批预先审批，锁定源版本和名单，逐件发布。首件正式发布事务使旧制度失效。

**架构**：扩展 schema 19 增加拆分批次与成员，成员复用现有修订提案状态及发布回执。原生草稿带分件 `channel`，发布器请求索引前持久登记目标 ID。读取门卫同时检查分件凭证与目标 ID。血缘图从已发布成员投影 `split_from`。

**技术栈**：Go、SQLite、Vue、原生已授权业务转发与 Markdown 草稿接口。

**依据**：[文档关联总体改造](../../design/文档关联总体改造.md#rel-05-制度拆分发布)。

## 约束

- 同租户、同库。旧制度为生效的在线 Markdown，锁定可核对的原始观测版本。
- 保持原生源码及既有发布接口。增量迁移只在扩展库，保持 `ext_lineage_edge` 既有枚举。
- 领取任务、对账和提交均复用持久状态。每份新制度形成独立修订族。
- 创建批次时拒绝会被原生清理的 Markdown 及非法标题，以便审批人核对将实际发布的正文。

## 接口

- `split_create` 接收 `document_id`、现有 `guidance_ids` 和 `split_parts: [{title,text}]`，2–8 份完整 Markdown。
- `split_approve`、`split_reject` 以批次 ID 和预期 revision 审核。既有 `revision_publish` 以分件提案 ID 逐份推进。
- `revision_list` 返回批次记录，`record_kind=split_batch`、`source_document_id` 和 `split_parts`。成员包含 `id/title/proposed_patch/status/revision/target_document_id/publish_error`。按分件 ID 读详情可得 `record_kind=split_part`。
