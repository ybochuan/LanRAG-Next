## 工作台关系语义

登记方向描述源文件对目标文件的作用。查询支持从两端查找，页面仍按同一个方向描述关系。条款冲突记录两端条款，箭头只表示登记顺序。

| 新增关联类型 | 登记方向 | 读者或管理者得到什么 |
|---|---|---|
| 修订 | 修订文件 → 被修订制度 | 确认修订依据。发布新版并替代旧版走版本治理。 |
| 解释 | 解释文件 → 被解释制度 | 找到正式解释文件。 |
| 相关候选 | 源文档 → 关联文档 | 登记一般业务联系。确认并通过查询核验后可用于导航。 |
| 引用依据 | 引用文件 → 被引用的依据 | 查到文件引用的标准、规定或其他依据。 |
| 实施细则 | 实施细则 → 上位制度 | 找到把上位要求落实成操作步骤的文件。 |
| 独立模板 | 模板文件 → 使用该模板的制度 | 找到制度配套使用的空白表格或模板。 |
| 补充说明 | 说明文件 → 被说明正文 | 展开阅读上下文、填写示例或常见问题。 |
| 内容提示 | 提示文件 → 被提示正文 | 展开阅读口径、适用条件或易错点。 |
| 制度废止 | 废止通知 → 被废止制度 | 审核后按指定时间执行，并保留治理记录。 |
| 条款例外 | 例外条款 → 通用条款 | 查到适用条件与锁定的两端条款，待审核确认。 |
| 条款冲突 | 登记的第一条款 ↔ 第二条款 | 核对冲突并人工裁决。登记顺序不决定优先级。 |

补充说明和内容提示首版登记整份文档，两端必须在同一知识库。读者从正文的「关联」或有效关联查询展开文件，使用已有文件预览权限。说明、提示和正文分别保留各自的生命周期和删除规则。填写示例、常见问题和易错提醒可作为文件标题或内容。段落定位需要跟随已登记版本，另行设计定位失效后的复核方式。

详情中的「补充依赖」从补充通知指向它依赖的主件。由系统维护的「附件归属」从附件指向主件。关系图还提供版本和来源关系，包括新版替代旧版、旧版合并至新版、分件拆分自旧版、派生内容来源于原内容、转换件转换自原件。

### 登记状态与当前有效性

- **待确认或待审核**表示记录已提交。一般相关候选等待确认，废止和条款关系遵循各自审核流程。
- **已登记或已确认**表示治理记录已经保存。登记状态保留记录历史。
- **当前有效**表示查询已核验两端文档的状态、适用时间和登记版本。说明或提示展开前重新核验关联，并通过原有文档权限读取。查询异常显示无法核验。
- **待复核或不可用**用于版本变化、停用、过期等导致当前有效查询不再返回的关系。记录保留在治理列表。列表要显示具体原因时，需要服务端提供已验证的原因。
- **已撤销**表示关系被主动撤销。附件可另有「旧版附件」或「已随主件删除」。废止可另有「待生效」和「已废止」，条款冲突可另有「待裁决」和「已裁决」。

### 关联板块的五项优化

1. **找到文件并能继续读。** 按知识库批量补齐结果标题，显示库名，提供「打开文档」「继续查询」。对正文收到的阅读关联，提供「展开说明」「展开提示」。
2. **用业务句子表达方向和有效性。** 例如「《紧急采购情形说明》为《采购管理规定》补充说明」。普通登记显示登记状态，有效查询才显示「当前有效」。治理记录中的复核原因由服务端返回。
3. **服务端先筛选再分页。** 以关系类型、登记状态和任一端文档筛选，提供待确认、待审核和待复核入口。验证满足条件的记录在第二页之后也能找到。
4. **串联查询、详情和关系图。** 从结果打开详情时定位到关联页。图以正在查询的文档为中心。返回恢复原查询、筛选和滚动位置。
5. **先选关系，再选两端。** 按类型用「说明文件」「提示文件」「正文文档」等业务名称标注两端。保存前显示登记方向，后续可在预览中显示选中的真实文件名及生效条件。

## 冲突点与阶段边界

- **权威边与导航关系**。引用、实施、模板都是显式文档关系，不驱动状态变更或级联删除。沿用业务关系记录并从中投影到图，避免为三个新类型扩大冻结的关键血缘枚举。多份制度可关联同一独立模板。
- **历史附件归属**。旧 Metadata 只能指明候选。只读清单必须复现原件提取，且实际附件字节与提取结果、原生哈希和旧记录 SHA-256 一致。写入模式必须重新核验审核清单。原件不可读、跨库、父件本身是附件、状态异常或哈希不一致时保留待查。
- **换版时的实体清理**。原生替换文件复用文档 ID，提取入口早于新版本完成解析。首版在完整提取后收起消失的附件，父件最终删除时统一实体清理。换版即物理删除、整库删除与数据源硬删的独立入口，需要另行验证原生完成时机和回滚条件。

## REL-05 制度拆分发布

**已确认规则（2026-11-08）**。同一份旧制度拆成多份新制度时，首份新制度正式发布成功即让旧制度从 `active` 变为 `superseded`。正式发布以新件完成索引、通过身份与版本校验、治理事务提交成功为准。此后旧制度退出普通检索，原件与历史血缘仍可按权限查阅。后续拆分件逐份生效，晚到或失败均不会恢复旧制度。

**冲突点**

1. 现有 `Publish` 在领取发布任务和最终提交时都要求源文档仍为 `active`。首份成功后继续走该条件，第二份会被拒绝。
2. 原生手工文档完成索引后，Observer 可能先初始化为 `active`。拆分件须有独立发布门卫，否则索引完成和治理提交之间会出现新旧制度同时可检索的窗口。
3. 冻结版的关键血缘枚举及版本族按线性修订实现，`ext_lineage_edge` 的约束不接受 `split_from`。每份新制度应保留独立的后续修订链。

**实施方案**

- 在扩展库增量登记同库拆分批次和分件。创建批次时锁定旧制度的观测版本，首版建议整批预先提交并审批，按已审批名单逐份发布。以实际完成治理提交的第一份为准，并发时由扩展写事务决定。
- 沿用原生 Markdown 草稿和发布 API。创建草稿时以 `channel` 携带分件凭证，登记目标 ID 后再由发布器请求索引。普通 RAG、Agent 检索及历史 MCP 均需核对发布事实，原生编辑器提前索引或改名也无法开放分件。发布器通过索引回执和源快照核对目标版本。原生管理入口继续按原权限展示草稿。远端结果未知时先对账，复用同一目标 ID。
- 首份提交在同一扩展事务登记分件的已发布版本、解除该件门卫、写入旧制度失效事件和审计。后续分件须证明确属同一已审批批次，且源版本与首份提交时的锁定版本一致。每件只登记自己的发布事实并解除自己的门卫。普通单件修订和拆分批次争用同一源版本时，在领取任务和最终提交均做冲突检查。
- 从已发布分件事实投影 `split_from` 到版本历史，方向为「新制度版本 → 旧制度锁定版本」。每份新制度保留独立版本族。保留既有关键血缘枚举、原生路由和普通单件修订的行为。首版的自动发布范围沿用现有 Markdown 路径。

| 实施顺序 | 文件范围 | 验收 |
|---|---|---|
| 1. 批次与发布 | `extensions/store/migrations/`、`extensions/business/{revision,native}.go` 及拆分发布实现 | 验证审批后锁定名单、同库约束、并发首份只失效一次。注入事务失败，确认旧件未失效且新件未开放。模拟草稿或索引响应丢失，重试复用原件。 |
| 2. 许可与血缘 | `extensions/retrieval/policy.go`、`extensions/lineage/{query,graph}.go` | 首份提交前旧件可用、待发布件被拦截。首份提交后旧件被拦截、首件可用。第二份失败时验证旧件持续失效；重试成功后两件均指向同一旧版本。 |
| 3. 管理界面与联合验收 | `extensions/management/business.go`、`frontend/src/views/{business,lineage}/`、`extensions/scripts/business_e2e.py` | 沿用现有修订列表、血缘图和已授权的管理写入转发。在隔离库使用真实 Core 和 Host 验证审批、逐件发布、旧件失效和共同祖先。回归普通修订、附件归属及同库授权。 |
