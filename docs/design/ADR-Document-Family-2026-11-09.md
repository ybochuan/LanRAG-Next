# 文档族、观察链与治理关系

FAM-01 至 FAM-04 已实现并通过隔离验收。真实语料校准和正式库启用条件见 [FAM-04 验收记录](../superpowers/plans/2026-11-10-fam-04.md)。参照 Frozen Architecture §8.1、§9.1、§9.2 和 §17.2。

## 现有事实与冲突

| 当前路径 | 实际含义 | 处理 |
|---|---|---|
| `ext_document_version_family`、`Registry.Refresh` | 每个 `(tenant, KB, doc_id)` 自动形成一条观察链。快照变化更新该链的观察头。 | 保留 ID、版本节点、FK 和原有读写。代码与界面逐步将这一概念称为“观察链”。 |
| `ext_revision_proposals.family_id` | 修订提案可沿用前次发布提案的旧 ID，外键仍指向某条原生观察链。 | 保留历史兼容，记录为旧发布链标识。后续提案另锁定经确认的业务族 ID。 |
| 图的 `family_id` 与原生 `gov:family:*` | 图取观察链 ID。标签从已发布提案推导，普通修订与拆分可能呈现不同口径。 | 读 API 分开提供观察链 ID 和业务族 ID。投影切换后只从经确认的业务族登记取值。 |

**C-FAMILY-01 · 权威边界。** Frozen 的版本族表达同一逻辑文档的线性演进。原有实现给每个原生文档单独建族，修订发布和标签投影又借用了相同的 ID。FAM-01 以加法迁移引入独立的业务族成员登记。发布、图及标签的读写切换和存量迁移分别由后续阶段处理，按 §17.2 保留设计评审和分库切换记录。

## 拟议模型

| 对象 | 身份与事实源 | 写入条件 |
|---|---|---|
| 观察链 | `observation_chain_id` 对应现有表的 `family_id`。每个原生文档一条，持有 `observed_head_version_node_id`。 | Registry 核验快照后自动追加版本。重新索引、正文编辑和观察头更新均可被记录。 |
| 业务文档族 | 新的 `business_family_id`，作用域为租户与知识库。由 `ext_business_document_families`、`ext_business_document_family_members` 登记，文档同一时刻至多归属同库一个业务族。 | 管理者创建命名族并显式确认加入、移出。已建立观察链且尚无成员登记的文档出现在 Host 的“未归族”列表。 |
| 发布版本 | `published_version_node_id` 指向已确认发布的不可变观察版本，业务族同时记录当前发布成员。允许族尚无发布头。 | 通过审核、切换事务并记录审计后更新发布头。原生文件变动触发重新核验，观察头不会自行变成业务发布头。 |
| 关系 | 带类型和方向的已确认事实，连接两端文档与锁定版本。血缘图、关系列表与标签从同一类型的当前事实投影。 | 人工声明或既有专用流程写入。候选和观察记录不触发治理。 |
| 生命周期 | `ext_lifecycle_events` 加 `ext_lifecycle_current`，日期来自文档标注。 | 由生命周期命令和已经确认的治理动作更新。工作台区分“业务族发布头”“当前允许检索”与“最近观察版本”。 |

例如三份分别上传的员工手册有三条观察链。管理者把它们加入“员工手册”后，工作台显示同一业务族的三份成员文档。确认“2026 版替代 2025 版”后，旧件失效，2026 版成为发布头。2026 版重新解析后可以出现更新的观察版本，业务发布头仍锚定已确认的版本。

## 确认、关系与工作台

- 加入或移出成员只改变业务族登记。加入前独立刷新原生快照，观察链记录这次核验。随后若成员登记遇到并发冲突或审计失败，已核验的观察记录仍可保留，成员登记、族修订号和回执一起回滚。发布头和参与待生效治理动作的成员需先通过对应业务流程解除约束。
- `supersedes` 从新版本指向被替代版本。界面展示两端、方向、生效日期和“被替代文档将失效”，由管理者确认。在到期且新件完成索引、两端版本和权限仍成立时，以同一事务写关键边、旧件生命周期、发布头、审计和 Outbox。过期的计划或版本漂移转待复核。并发替代通过族修订号与版本锁定检测冲突。撤销已生效替代保留历史，恢复旧件需要独立治理操作。
- `supplements`、`amends`、`interprets`、`related_to`、`cites`、`implements`、`template_for` 和条款关系按各自规则确认。补充通知可出现在族详情的外部关联区，仍拥有自己的身份。附件归属继续使用已核验的 `ext_attachment_links` 与随主件清理流程。拆分保持首个分件发布即使原件失效的规则，分件的业务归属另行确认。废止继续由有审批和日期的专用流程执行。
- 工作台以族和文档为入口。左侧显示族与未归族文档，详情并列显示成员、关系、生命周期及操作历史。首版复用现有管理入口，原有地址继续服务直接导航；版本历史和内容溯源保留独立查询语义。
- 候选分为“建议归族”和“建议关联”。按库从标题与年代、语义相似度、引用、元数据和结构信号生成，展示原因与分项得分。确认、忽略均可追踪；批量确认逐项核验，治理动作仍需单独确认。异步计算与上传解耦，默认库内。先用每库 20–50 组人工标注校准，报告精确率与召回率，通过 Frozen §9.2 的 0.70、0.60 门槛后再用于验收。

## 迁移与验收顺序

| 阶段 | 改动与验收 |
|---|---|
| FAM-01 术语和模型 | 评审 ID、状态、成员约束和读 API 兼容层。以加法迁移引入可手工维护的同库业务族。验证三份文档可以同族、重复操作幂等、跨库拒绝和旧版本 FK 完整。 |
| FAM-02 受控替代 | 复用普通修订的发布门卫和原子治理事务。覆盖确认前不影响旧件、时间到达且新件可用后切换、审批后任一端修改导致待复核、两份竞争发布只有一个能改头、故障回滚。 |
| FAM-03 存量盘点与切换 | 只读按真实 `supersedes` 边和已发布提案生成候选清单，列出冲突、孤立和拆分记录。管理员确认后按库登记，保留旧 ID 映射。快照验证计数、FK、状态和审计，重放只产生同一结果。图与标签按库切换；标签投影可重放，不能用标签反向确定成员。 |
| FAM-04 工作台与建议 | 在同一页面管理成员、内部与外部关联、日期、状态和审计。验证角色权限、撤销后当前图消失而历史保留、候选忽略持久化、未确认时权限不变，以及每库校准指标。 |

### FAM-01 接口

- 写入使用既有原生 JWT 管理路径 `PUT /api/v1/knowledge-bases/:id/lifecycle/business/:action`。`family_create` 使用 `expected_revision=0` 和 `business.payload.family_label`，`family_member_add`、`family_member_remove` 使用族修订号、`business.id` 和 `business.payload.document_id`。所有写入提供 `operation_id`，同一请求重试返回原回执。并发更新或隐式跨族移动返回冲突。
- 服务器间查询使用 `POST /management/lifecycle`，动作是 `business_family_list` 和 `business_family_members`。`business.id` 可筛选指定族，查询成员时省略它会列出已观察的未归族文档。租户、知识库和分页沿用现有管理合同。浏览器通过原生 JWT 管理路径的 `family_list` 和 `family_members` 读取。
- 以 `AGENTRAG_FAMILY_E2E=1` 运行 `extensions/scripts/governance_e2e.py` 可验证真实 Core/Host 的上传、写入与查询。扩展测试另覆盖跨库拒绝、同修订号并发更新、审计失败回滚和 schema 22 升级保留旧提案外键。

### FAM-02 接口

- 原生写动作 `family_replace_create` 接收 `business_family_id`、`family_revision`、新件 `document_id`、旧件 `target_document_id` 和 `effective_at`。两端均须已索引、有效并处于同一族。已有业务发布头时，旧件须对应其发布版本。
- `family_replace_approve` 用提案 ID、修订号和 `second_confirmation=true` 预约。确认前新旧件沿用原可见性。预约期间发布门卫暂扣新件。到期核对后应用，发现确定的版本或成员变化则转待复核，取消或转待复核时解除预约门禁。
- Host 读动作 `business_family_replacements` 按 `business.id` 的业务族 ID 列出提案和历史。族列表额外返回 `published_document_id` 与 `published_version_node_id`。`AGENTRAG_FAMILY_E2E=1 AGENTRAG_FAMILY_REPLACEMENT_E2E=1` 可在治理 E2E 中验证真实定时切换。
- 替代端点限主件，核对当前原生元数据和持久附件归属。两端不能互相依赖。到期复核同时刷新第三方补充依赖，明确缺失或版本漂移转待复核，未确定的网络故障保留预约等待重试。
- 若原地编辑或旧版修订／拆分工作流先改变已发布成员，业务发布头仍记录原审批版本，新的同族替代需先处理该漂移。旧发布流程的业务族接续纳入后续切换。现有血缘查询仍受遍历深度限制，长链需在工作台分段查阅。

### FAM-03 确认回填与分库投影

- Host 读动作 `business_family_backfill_plans` 按库分页，`business.id` 可筛选一个旧 family ID。只有发布提案、两端版本身份和关键替代边一致且组成线性链时才给出候选指纹。缺边、歧义、循环或分叉返回待复核。拆分提案单独列出。
- 预览只读历史证据。确认时重算指纹、验证目标族修订号与成员约束，再写入映射与审计。发布指针采用经确认的历史版本，图与标签按知识库切换。已有业务发布头始终阻断旧发布流程。
- 启用投影时只处理已登记成员和曾纳入业务族投影的文档。未归族与已明确移除是不同的状态，前者保留已有标签。允许只回填完成核对的业务族，未回填的文档可独立保留。

### 复审后的边界

- 用户可见的“文档族”只指人工登记的业务族。单文件允许不归族。旧表名、提案外键与兼容响应中的 `family_id` 保留其技术语义。旧图把这项标为“观察链”，工作台按 `business_family_id` 组织。切换只影响旧读模型和标签投影。
- 移除成员保留状态、时间及原因，同一族重入复用登记，加入、移除与重入仍各有独立审计。迁移 026 为已登记成员补录当前状态，早期移除记录仍在既有操作审计。
- 带附件的主件可以作为替代端点。原生元数据和持久归属用于识别端点本身是否为附件。旧主件失效时，其附件由父件门禁拒绝，保留原归属。
- 替代创建、确认和到期分别重新核对两端，事务内将批量元数据的解析状态、启用状态、渠道和文件指纹与锁定版本对照。原生库与扩展库分开提交，仍需在实际生效时复查。成员可登记已解析的历史主件，改变发布头则要求明确的原生启用状态。
- 当前关系图只投影有效的补充声明，历史边继续留档。原生删除/恢复的对账、发布头恢复和 `superseded` 历史搜索另行确定状态与权限规则。

## 审查项归属

| 问题 | 处理原则 |
|---|---|
| 日期、原生停用和发布窗口 | 许可时核对日期和当前原生状态。普通与拆分发布先绑定禁用草稿再索引，完成事务前遮蔽目标。日扫仍负责写正式生命周期事件，读请求直接使用当前时点。 |
| MCP 范围扩张 | 补充件必须在原生请求范围内。已核验且同库的附件归属可继承主件许可，直接授权附件时屏蔽超出范围的主件信息。 |
| 状态词表与多入口写入 | 后续统一状态常量、动作及允许迁移。先审计存量状态，再收紧写入白名单。区分“归档历史查询可见”和“普通 RAG 可用”，单独决定 `superseded` 的历史工具语义。 |
| 补充撤销仍出现在图中、关系双写 | 先让当前关系图读取有效声明及其边凭证，历史图保留原证据。声明、关键边与审计保持同一事务。为现有关系定义明确的幂等键、撤销及投影回归，逐类型切换。 |
| 衍生件分级、来源头与观察序列 | 保留版本节点的共用身份及来源证据，单独区分观察序列与副本账本序列。先确定 `rendition_of` 的投影边类型，再统一跨读面的命名。 |

旧版发布回执靠原生 `api` channel 和完整确定性标题匹配。未绑定且标题已被改写的旧目标需要通过只读盘点和人工核对识别。MCP 附件目前沿用每个命中项最多 32 条的共享列表，随后才收窄到原生授权范围；大量旧附件可能挤掉可返回项。需要分页时，在工作台与 MCP 的读模型中将授权过滤放在分页之前。
