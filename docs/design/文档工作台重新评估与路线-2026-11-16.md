# 文档工作台重新评估与后续开发路线（2026-11-16）

## 背景

整改项目要求「围绕后续重新设立的文档工作台重新评估后续开发」。本文件记录对现有工作台实现的现状核对、发现的缺口，以及据此重排的后续开发路线。核对基于本机真实生产环境（生产 Core 18880、生产 KB `164bfd73-d231-4d5c-994e-057ac0cdf48a`、生产静态资源目录），未使用隔离或虚拟环境。

## 现状核对

### 入口与路由

侧边栏只有一个治理入口：`frontend/src/stores/menu.ts` 中 `{ titleKey: 'menu.documentWorkbench', icon: 'artifact', path: 'documents' }`。旧治理地址（`lifecycle`、`families`、`associations`、`feedback-governance`、`revisions`、`lineage`）统一重定向到 `name: 'documents'` 并保留 `view` 参数：

```text
{ path: view, name: view, redirect: to => ({ name: 'documents', query: { ...to.query, view } }) }
```

因此 URL 契约是稳定的：`?view=<工作区>` 是唯一的视图寻址方式，旧链接与书签仍然落到同一视图。

### 工作台的两层结构

`frontend/src/views/lifecycle/LifecycleView.vue`（37KB）承载两层：

**列表层** `tabs`：`全部文档`、`待复核`、`库级规则`。

**工作区视图** `workspaceView`（由 `route.query.view` 解析，接受 5 个值）：

| view | 承载组件 | 职责 |
|---|---|---|
| `families` | `FamilyWorkspaceView.vue`（40KB） | 业务族与版本族工作台、族建议 |
| `associations` | `BusinessView.vue`（36KB，`section='associations'`） | 关联关系、引用、附件归属 |
| `feedback-governance` | `BusinessView.vue`（`section='feedback-governance'`） | 反馈待审、指导与抽样复核 |
| `revisions` | `BusinessView.vue`（`section='revisions'`） | 修订提案与发布 |
| `lineage` | `LineageView.vue` | 单库血缘图 |

`BusinessView.vue` 已用一个 `section` prop 承载三个业务面，收敛工作已部分完成。

### 文档详情层

同一文件内另有 `detailTabs`：`生命周期`、`版本族`、`关联关系`、`关系图`、`治理记录`、`关联建议`、`修订发布`，按单文档维度复用上述同一批组件。

## 发现的缺口

### 缺口一：四个工作区视图没有顶层入口（已修复）

顶层 tab 只有「全部文档 / 待复核 / 库级规则 / 反馈审核」四项，而 `workspaceView` 实际接受 5 个值。**`families`、`associations`、`revisions`、`lineage` 没有顶层入口按钮**，只能靠手改 URL 或旧路由跳转到达。这是「工作台」作为统一治理入口的最直接障碍：用户看不到关联关系、修订发布与业务族，只能靠记忆拼 URL。

本轮修复：新增 `workspaceTabs` 声明，5 个工作区视图全部成为顶层 tab，URL 契约不变（仍为 `?view=<view>`）。改动只涉及 `frontend/src/views/lifecycle/LifecycleView.vue`，不触碰任何组件接口、路由结构或后端契约。

### 缺口二：工作台与文档详情两层重复承载同一批治理面

「关联关系」「修订发布」既出现在工作区层（按库浏览），又出现在文档详情层（按单文档浏览）。两者复用同一组件与同一 API，但入口语义不同。目前没有明确的「以哪个为准」的规则，也没有在工作台层说明详情层与库级视图的关系。**这是重新设立工作台时需要用户确认的产品决策，不宜由实现方默认。**

### 缺口三：视图切分与实际治理能力不齐

按本次盘点，以下能力**没有**工作台入口，全部落在旧页面或无入口：

- **T4 实际文件写入 producer**（写→归档→跨轮读、覆盖不缩源、ACK 未知不重放、重启撤销）：能力未接线，尚不能进工作台。
- **M2 外部通知与生产配置入口**：仅有本地固定日志（`cmd/review-alerts`），没有可投递的通道，因此无法在工作台呈现「通知已送达」这类状态。
- **M1.5 检索基线与重排降级**：没有可观测的检索质量视图，无法在工作台呈现 Recall/MRR 或降级状态。
- **M4 Agentic 评估与 M4-CAL 独立标注**：评估结果与人工标注结论尚无落库与呈现位置。

也就是说：**剩余整改项里，凡是「已接线但缺界面」的可以直接进工作台；凡是「能力未接线」的必须先接线才有界面。** 这一区分决定了后续顺序。

### 缺口四：Agentic 评估的答案质量没有落库位置

`extensions/cmd/agentic-eval` 已能产出每题的报告（轮次、工具序列、答案文本），但报告只落在 `tmp/` 下的文件里。工作台没有「评估」视图，冻结架构要求的「人工评分」也没有承载对象。人工评分若要可复核，必须有持久化与呈现。

## 重新评估后的开发路线

按「先接线、后界面；先可观测、后可评分」重排：

| 顺序 | 整改项 | 是否依赖云端 LLM | 工作台归属 | 前置条件 |
|---|---|---|---|---|
| 1 | **P1 T4-04 producer 接线** | 否 | 详情层新增「来源与副本」标签（写入记录、归档、撤销） | 无 |
| 2 | **P2 M2 外部通知与生产配置入口** | 否 | 工作台新增「通知投递」视图；库级规则页补生产配置 | 需确认投递通道形态 |
| 3 | **P9 T4-01/02 故障矩阵** | 否 | 无界面需求，证据进 `docs/evidence/` | P1 完成 |
| 4 | **P4 M1.5 检索基线** | 否 | 工作台新增「检索质量」视图（Recall/MRR、降级状态） | 需确认基线样本来源 |
| 5 | **P8 ingest 原生事件 Hook** | 否 | 详情层生命周期标签的数据来源增强 | 需确认原生事件契约 |
| 6 | **P7 M2-COPY-LINEAGE 原生接线** | 否 | 详情层「来源与副本」标签的落地路径 | P1 完成 |
| 7 | **P12 M5-BINARY 生产故障注入** | 否 | 无界面需求 | 无 |
| 8 | **P15b Agentic 评估结果持久化与呈现** | 部分 | 工作台新增「评估」视图（轮次、工具序列、人工评分） | 云端账户恢复；评分口径需用户确认 |
| 9 | **P11 M5-ACCEPT 真实冷静期与质量回归** | 是 | 反馈治理页补抽样复核明细与质量指标 | 云端账户恢复；需真实等待 24/48h |
| 10 | **P13 M4-CAL 独立双人人工标注** | 否 | 「检索质量」视图内的标注集与复核流 | 需人工标注者参与 |

### 被排除或暂缓

- **血缘图（M6）**：按用户指示暂不处理。工作台的 `关系图` 入口保持现状，不做改造。
- **运维工程遗留**（ONEKEY-02、TEST-MODEL-PORT、TEST-NATIVE-RACE）：按用户指示暂不处理。

### 需要用户决策的三项

1. **工作台与文档详情的重复面**：关联关系、修订发布在两层都有入口，是保留两层（库级总览 + 文档内聚焦），还是收敛为一处？
2. **M2 外部通知的通道形态**：邮件、站内信、还是仅本地待办队列？这决定「通知投递」视图的数据模型。
3. **内置 Agent 轮次上限**：生产 `builtin-smart-reasoning` 的 `max_iterations` 为 50，冻结架构要求 3–4。改动会影响生产问答行为，需单独授权。

## 边界

- 本文件不改变冻结架构，不新增原生接口，不改扩展库 schema。
- 「工作台 + 业务面合并」这类深度重构不在本轮范围内；本轮只补齐缺失的入口，组件接口与路由契约保持不变。
- 浏览器端未完成登录态下的点击验证：浏览器的安全策略拒绝在密码字段输入，本轮改以生产 bundle 内容核验加 API 契约核验作为生产验证依据，未声称完成浏览器交互验收。
