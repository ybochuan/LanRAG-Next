# LanRAG-Next 统一数据架构与信息治理重构专项方案 v2.0

**项目：** LanRAG-Next
**方案版本：** v2.0（核心可修改版）
**方案日期：** 2026-11-28
**代码基线：** sync/v0.9.1
**基线提交：** e263b528e5fccbae438a32a14470e8747d5f8c1f
**方案性质：** 架构重构专项设计 / 评审稿
**目标部署：** Windows 桌面端（主要） + WSL2 Ubuntu + SQLite Lite
**架构方向：** 单物理数据库、双逻辑业务域、核心最小补丁、扩展 shared 模式

> 本版的前提是用户已明确授权修改原生 WeKnora 核心文件。首批核心改动仅限 CP-01（迁移失败关闭）、CP-02（SQLite 版本与连接门禁）和对应的 CP-05 测试与记录；CP-03/04 标签接口按评审意见移出首批，列为 P4 可选且需另行评审，不修改 RAG 检索算法、解析器、调度器或模型调用逻辑。v1.0 与上一版基于双库约束的 v2.0 草案，以本文件为准。
>
> **评审状态（2026-11-28）：** 已按只读评审修正五处：回滚必须支持共享库拆回双库；Host 保持 synchronous=FULL，并先核对 SQLite 3.46.1 的 WAL-reset 风险；标签整组替换不得按 50 个 ID 分批；首个原型固定 native 51 / ext 41 并用真实对象清单；锁策略与生命周期终态不进入首批。本稿是设计评审稿，不是生产切换手册。

## 0. 结论摘要

### 0.1 最终建议

v2.0 采用：

**单物理数据库 weknora.db + 双逻辑业务域 + Core/Host 两进程 + 扩展表 ext_ 前缀共存。**

具体含义：

1. 运行时只保留一个 SQLite 文件，即 weknora.db；agentrag_ext.db 不再作为运行时数据库，只作为迁移前备份和回滚归档。
2. 原生表仍由 WeKnora Core 管理；扩展治理表仍由 Extension Host 管理；表所有权不因同库而改变。
3. 扩展表不合并进原生表结构，不修改原生表定义；扩展表以 ext_ 前缀直接建在 weknora.db 中。
4. 原生迁移继续由 Core 的 golang-migrate/schema_migrations 管理；扩展迁移继续由 Host 的 ext_schema_migrations 管理；两套迁移目录不混用，启动时由一个 release manifest 配对版本。
5. Extension Store 新增显式 shared 模式：允许原生表与 ext_ 表共存，但采用真实对象清单与表名边界校验，不删除原有独立库模式，也不放宽默认安全检查。
6. 保留 Core/Host 进程边界、Bridge v1、Outbox、Saga 和现有 RAG 门禁；不将扩展代码整体搬入 internal/，不把 Host 变成 Core 的内部包。
7. Core 修改首批只解决单库真正需要的启动/连接问题：CP-01（迁移失败必须 fail-closed）和 CP-02（SQLite 版本与连接门禁）。标签写入接口 CP-03/04 移出首批，因为旧整组替换接口不能被新 CAS 约束，且 50 ID 上限不可拆分。
8. 立项顺序：先做不依赖 shared 的治理读取和标签去投影（P0.5）；shared SQLite 只进入隔离原型（P1）；在对象清单、拆回演练和 WAL 压测通过前，不进行生产切换。

### 0.2 八个评审结论

1. **v1.0 的方向正确，但实现前提写错了。** v1.0 把“单库”写成了“改两个环境变量指向同一个文件”。当前 extensions/store/sqlite.go 的 checkOwnership 会拒绝任何非 ext_ 表，launcher_config.py 也会拒绝相同路径。但这两处都是扩展侧代码，不是上游限制；在核心可修改的前提下可以新增 shared 模式，而不是删除安全检查。
2. **扩展表数量不是约 30 张。** 代码基线实际有 41 个扩展迁移、90 张唯一 CREATE TABLE 名称、91 张物理扩展表。v1.0 的清单只能作为业务域示例，不能作为迁移清单。
3. **原生和扩展身份类型不一致。** 原生 000000_init 使用 tenant_id INTEGER；扩展 schema 中 89 处 tenant_id 是 TEXT，另有 4 处是 INTEGER。单库后必须统一逻辑身份契约，并在热查询路径显式处理类型，否则索引和跨表比较会退化。
4. **生命周期不是 v1.0 写的七态。** 实际 lifecycle/machine.go 只有 pending、scheduled、active、stale 四个状态；revision.go 和 repeal.go 会直接追加 superseded、archived。v2.0 记录 pending、scheduled、active、stale、superseded、archived 六态，但首批保持现有转换；TransitionTerminal 和新增状态字典另排 P4，需业务确认。quarantined、withdrawn 属于反馈/指导状态，不应混入生命周期。
5. **标签的 tags:null 前提已部分过时，但整组替换仍是硬风险。** 代码新增 GET /api/v1/knowledge/{id}/tags/ids 显式标签 ID 接口；成功返回必须 tags 非 nil，否则报错。PUT /api/v1/knowledge/tags 的 50 ID 是单次整组替换上限，底层 SetKnowledgeTags 是先删后插；拆成 50＋1 会把整组覆盖成最后一批，不能分批。先退出治理标签投影，标签写入接口另排。
6. **v1.0 的迁移备份工具并不存在。** migration-backup、integrity-report、ATTACH 迁移器都只是设计目标；v2.0 必须先把它们作为 P2 交付物实现，不能把设计写成已实现。
7. **原生迁移失败是 fail-open。** internal/container/container.go:1112-1119 只记录 warning，然后继续启动。单库模式下这会让 Core 带着错误 schema 运行，v2.0 必须改为 fail-closed。
8. **单文件不等于跨进程 ACID。** Core 和 Host 仍各自持有 SQLite 连接；同一文件只保证 SQLite 层面的写锁串行，不保证两个进程的跨域事务。所有跨域操作仍通过 Outbox、Saga、回执和对账完成。

### 0.3 关键决策

| 编号 | 决策 | 内容 |
|---|---|---|
| D1 | 单物理库 | 运行时只使用 weknora.db；agentrag_ext.db 退出运行时 |
| D2 | 双逻辑域 | 原生表归 Core，ext_ 表归 Host，禁止越界写入 |
| D3 | 核心最小补丁 | 首批仅 CP-01/CP-02；CP-03/04 标签接口 P4 可选；不改 RAG、解析、调度 |
| D4 | shared 模式 | Extension Store 新增 OpenShared，保留 strict 模式作回滚 |
| D5 | 双迁移目录 | schema_migrations 与 ext_schema_migrations 分离，用 release manifest 配对 |
| D6 | 跨域 Saga | 单库不承诺全局 ACID；生命周期/标签/附件跨域仍用持久意图与对账 |

## 2. v1.0 逐项评审

### 2.1 v1.0 正确的部分

以下内容应保留：

1. 双库确实造成了跨库同步、标签投影、附件归属、生命周期展示的额外复杂度。
2. 单物理库、统一文档身份、明确数据所有权、治理操作审计同事务、修订发布 Saga、Outbox 幂等、投影不是事实源，这些方向正确。
3. 标签应分为治理事实与业务分类，治理状态不应继续依赖 gov:state:* 标签。
4. 迁移必须停写、备份、离线迁移、核验、切换，不能直接生产双写。
5. Win10/WSL2/SQLite Lite 的桌面优先目标不变。

## 3. 目标与边界

### 3.1 目标

| 编号 | 目标 | 验收含义 |
|---|---|---|
| G-01 | 单物理数据库 | 运行时只打开 weknora.db，不再打开 agentrag_ext.db |
| G-02 | 统一文档身份 | tenant_id + knowledge_base_id + document_id 三元组贯穿原生与扩展 |
| G-03 | 双逻辑域 | Core 只写原生表，Host 只写 ext_ 表；Host 原生读取只读 |
| G-04 | shared 模式 | Extension Store 能安全打开含原生表的数据库，未知表仍拒绝 |
| G-05 | 迁移可恢复 | 双库到单库迁移可停写、可核验、可回滚 |
| G-06 | 标签简化 | 治理状态不再依赖 gov 标签；业务标签保留原生标签 |
| G-07 | 查询统一 | 工作台/阅读中心/附件/版本族可在同库聚合 |
| G-08 | RAG 不退化 | Recall、门禁准确率、历史误召回率不劣于基线 |
| G-09 | 故障关闭 | 治理库不可用、schema 版本不符、迁移失败均 fail-closed |
| G-10 | 维护简化 | 一套路径、一套备份、一个数据库文件；核心补丁有清单、有测试 |

### 3.2 非目标

本次不进行：

- 不重写 WeKnora 原生知识库、文档上传、解析、切块、嵌入、RRF、Agent 调度。
- 不取消 Core/Host 进程边界。
- 不取消 Bridge v1、Outbox、Saga。
- 不把 90 张扩展表并入原生业务表定义。
- 不把扩展代码整体搬入 internal/。
- 不将 PDF/DOCX/XLSX 二进制存入 SQLite。
- 不删除生产数据、不在未备份时切换。
- 不因单库而取消租户、知识库、文档权限校验。
- 不通过修改原生标签表结构来承担治理状态。

### 3.3 为什么允许改 Core，但仍限制补丁范围

用户已授权修改原生核心文件，因此 v2.0 不需要像上一版那样把 checkOwnership 当作不可改的硬约束。但“可改”不等于“应该大改”：

- 原生 52 个迁移版本、81 张表；任何 schema 重写都会与上游同步冲突。
- 扩展 41 个迁移、90 张表；搬入 internal/ 会造成模块边界和测试体系崩溃。
- 单库真正缺的是启动门禁、连接参数和可验证的 SQLite 版本，不是重写 RAG 或解析。
- 首批只做 CP-01/CP-02；CP-03/04 标签接口不进入原型，避免把“新 CAS 可控”误当成旧整组覆盖已安全。

### 4.2 数据库职责

| 对象 | 归属 | 写入范围 | 读取范围 |
|---|---|---|---|
| weknora.db | 单物理库 | Core 与 Host 均连接，但按表所有权写入 | 各自按权限读取 |
| 原生表 | WeKnora Core | Core 原生业务写入 | Host 通过只读连接读取 |

| schema_migrations | WeKnora Core | Core 迁移器写入 | Core 启动检查、Host 只读验证 |

### 4.3 进程边界

保留两个进程：

- Core：原生文档、标签、索引、检索、Agent、原生权限、原生 MCP。
- Host：生命周期、版本族、附件、反馈、修订、审计、Outbox、门禁、治理 API。

单库只改变存储位置，不改变进程边界。跨进程业务仍通过 Bridge v1、HTTP、Outbox 和 Saga 协调。

### 4.4 连接角色

| 连接 | 所属 | 权限 | 说明 |
|---|---|---|---|
| Core Native Writer | Core | 原生表读写 | 保持现有 GORM 连接 |
| Core Native Reader | Core | 原生表只读 | 现有读连接池 |
| Host Extension Writer | Host | ext_ 表读写 | 专用单写连接，BEGIN IMMEDIATE |
| Host Extension Reader | Host | ext_ 表只读 | 现有 4 个只读连接 |
| Host Native Reader | Host | 原生表只读 | 独立只读连接，允许读取原生表；不得写 |

SQLite 没有表级授权，表所有权通过 Repository、SQL 执行器、代码审查、迁移检查和自动化测试落实。

### 4.5 SQLite 参数

初始值维持现有基线，不在 P1 改连接池大小：

| 参数 | 初始值 | 说明 |
|---|---|---|
| journal_mode | WAL | Core/Host 一致 |
| synchronous | Host 保持 FULL（OpenDurable）；Core 共享模式显式 FULL | 不得为了性能把 Host 降为 NORMAL；迁移期间同样保持 FULL |
| busy_timeout | 5000ms | 两进程一致 |
| foreign_keys | ON | 两进程一致 |
| cache_size | -64000 | 两进程一致 |
| wal_autocheckpoint | 1000 | 两进程一致 |
| Core MaxOpenConns | 1（保持） | 单写者，先保持基线 |
| Host Writer | 1/1 | BEGIN IMMEDIATE |
| Host Reader | 4/4 | 只读 |
| SQLite 版本 | 候选二进制必须记录 sqlite_version() / sqlite_source_id() | 见下方 WAL-reset 门禁 |

单文件仍然只有一个写锁。P1 不得以“单库”为理由放宽 busy_timeout 或盲目增大 Core 连接池。

**SQLite WAL-reset 门禁：** 官方 WAL 文档指出，WAL-reset bug 影响 3.7.0 至 3.51.2，修复版为 3.51.3，另有 3.44.6、3.50.7 的回移；当前证据记录的 SQLite 3.46.1 落在影响区间，而共享单文件正好引入同文件多连接写/checkpoint 场景。P1 必须在候选二进制上执行 `SELECT sqlite_version(), sqlite_source_id();` 并写入证据；未使用修复版或包含修复回移的构建时，只能做单写者原型，不得进行共享 WAL 多连接压测，更不得生产切换。来源：https://www.sqlite.org/wal.html 。

### 4.6 单库不承诺全局 ACID

即使 Core 和 Host 打开同一个文件，它们仍是两个进程、两个 SQLite 连接：

- Host 内的 event + current + outbox + audit 可以是同一事务。
- Core 内的原生文档写入和标签写入可以是同一事务。
- Host 调用 Core 标签接口后，Host 再写 ext_ 表，是第二个事务。
- 跨进程操作不能声明为全局 ACID；必须使用持久意图、回执、Outbox、Saga 和对账。

这是 v2.0 的核心边界，不得用“同库”掩盖。

### 4.7 Extension Store shared 模式

新增 extensions/store/shared_database.go，提供显式入口：

~~~text
OpenShared(ctx, absolutePath) (*DB, error)
~~~

实现要求：

1. absolutePath 必须是已存在的普通文件；拒绝空字符串、:memory:、file: URI；shared 模式不自动创建空库。
2. 先用只读连接读取 PRAGMA database_list 和 sqlite_schema，确认实际打开文件与传入路径一致。
3. 允许对象集合不再写死 81 张表。用带真实 FTS5/sqlite-vec 索引的数据库副本生成 native object manifest，覆盖普通表、索引、触发器、视图、FTS5 虚表及其影子表、vec0 虚表及其影子表、schema_migrations、sqlite_sequence、sqlite_stat1；shared 启动时按 name + type + SQL hash 比对，未知对象一律拒绝，保留严格防线。
4. 校验原生 schema：schema_migrations 版本必须为 51，dirty 必须为 0；缺失原生对象或版本不符返回 ErrNotSharedDatabase。AUTO_MIGRATE=false 时不得把空库或半迁移库当 shared 打开；必须先由独立迁移命令完成 51/0，再启动。
5. shared 模式使用独立迁移入口：要求 ext_schema_migrations 已存在且版本=41；禁止走 adoptManualSchema 的“无历史即整库比对”路径；扩展迁移只能创建或变更 ext_ 表，禁止 ALTER/DROP 原生对象。
6. 连接池：writer 1/1、reader 4/4；writer 事务使用 BEGIN IMMEDIATE；reader 使用只读连接。
7. 现有 OpenDurable 保持 strict 模式，作为测试、独立库和回滚路径；只有 AGENTRAG_STORAGE_MODE=shared 时才走 OpenShared。
8. ViewNative 在 shared 模式下不再 ATTACH 第二个物理文件；直接使用同一个 weknora.db 的原生只读连接，或统一改由 NativeReader 提供。任何代码不得把 agentrag_ext.db 当作运行时 ATTACH 目标。
9. 首个原型使用真实生产库副本建立对象清单，固定 native 51 / ext 41，不应用 042-044 候选迁移；原型只能打开副本，不得直接在生产库创建 ext_ 表。

shared 模式不删除 native 表、不接管 native 迁移、不改变原生表结构；它只解决“扩展表能否与原生表同库”的问题。

## 7. 生命周期

### 7.1 实际状态

代码事实：

- extensions/lifecycle/machine.go:17-20 只有 Pending、Scheduled、Active、Stale。
- extensions/business/revision.go:309-315 直接 AppendTx(ToState="superseded")。
- extensions/business/repeal.go:162-170 直接 AppendTx(ToState="archived")。
- ext_lifecycle_events.to_state 只有 length>0 CHECK，没有枚举约束，所以任意字符串可以写入。
- ext_lifecycle_current.last_event_id 有复合外键；007 迁移有触发器保证当前状态等于最新事件。

v2.0 定义六态：

~~~text
pending
scheduled
active
stale
superseded
archived
~~~

quarantined、withdrawn 是反馈/指导状态，不是生命周期状态。

### 7.2 状态转换

| 起点 | 终点 | 触发 |
|---|---|---|
| pending | scheduled | effective_from 在未来 |
| pending | active | 解析完成且未过期 |
| scheduled | active | effective_from 到期且未过期 |
| active | stale | effective_until 到期 |
| pending/scheduled/active | stale | 到期兜底（按现有规则） |
| active | superseded | 仅现有 revision 发布，保持现有规则 |
| active | archived | 仅现有 repeal 废止，保持现有规则 |

首批不扩大现有转换，不新增 stale -> superseded 或 stale -> archived；TransitionTerminal 和状态字典另列 P4 评审。

不允许：

- 直接 Update ext_lifecycle_current 绕过事件。
- 从 archived 自动复活。
- 用 quarantined 标签或字符串代替生命周期状态。
- 在没有事件和 outbox 的情况下修改当前状态。

### 7.3 TransitionTerminal（P4 候选，不进首批）

新增 Host 服务（仅作 P4 设计草案，不在首批实现）：

~~~text
TransitionTerminal(scope, fromState, toState, reason, actor, requestID)
~~~

要求：

1. 只覆盖现有 active -> superseded（修订发布）和 active -> archived（废止）；不得把 stale 等新增范围带入首批，不得改变现有业务语义。
2. 同一事务写 event + current + outbox + governance audit。
3. 使用 CAS/expected current state 校验；冲突返回明确错误。
4. P4 批准后，revision.go 和 repeal.go 才评估改调 TransitionTerminal；首批保留现有 AppendTx 路径。
5. 事件 payload 记录来源提案、发布回执和操作者。

### 7.4 事务和一致性

保留 001_lifecycle.sql 的 event/current/outbox 结构。AppendTx 仍由外层 db.Write 提交；首批保持现有 revision.go/repeal.go 直接 AppendTx 的转换。TransitionTerminal 如获 P4 批准，必须复用同一事务边界，不得先写 current 再补事件。

| 生命周期状态 | 生命周期事实 | 否 |
| 版本状态 | 版本族/替代记录 | 否 |
| 文档关系 | 关系事实 | 否 |
| 业务分类 | 用户/管理员 | 是 |
| 受控词表 | ext_kb_tag_mapping（canonical_name -> 原生 tag_id） | 可绑定原生标签 |
| 个人标签 | 用户 | 是 |

### 8.2 现有代码事实

- extensions/taggov/http_store.go:59-104 优先 GET /api/v1/knowledge/{id}/tags/ids；成功后必须 tags 非 nil，且 knowledge_id、tenant_id、kb 匹配。
- 回退 GET /api/v1/knowledge/{id}，tags 为 nil 时返回 ErrAmbiguousTags。
- PUT /api/v1/knowledge/tags 的 ReplaceTags 最多 50 个 tag ID；SetKnowledgeTags 是先删除该文档全部标签关系、再插入本批，50 ID 是整组替换上限，拆成 50＋1 只会留下最后 1 个，不能分批。
- AddKnowledgeTagRelations 只做增量增加，不能删除；可作为 P4 受管标签关系接口的基础，但当前没有删除能力和 managed 标记。
- extensions/taggov/writer.go 是单写者内存队列，不是持久 Outbox 替代。
- TagPreconditionError、precondition.go、governance health 在未提交工作树中，不能当作已提交能力。

### 8.3 v2.0 标签方案

1. 保留原生标签给业务分类和个人标签。
2. 治理状态不再写 gov:state:*、gov:family:*、gov:relation:*；工作台从生命周期/版本族/关系事实读取。
3. 受控业务词表使用现有 ext_kb_tag_mapping（tenant/kb/canonical_name -> tag_id）；如后续确需独立分类/显示名，再新增 ext_tag_taxonomy 并单独编号，不混入 P1。
4. 首批先完成治理徽标和筛选从事实读取（T0-T4），随后停止 gov 标签投影；此时 TagGov 不再需要写入治理标签。
5. 如 T4 后仍有兼容消费者必须写原生标签，只能在 P4 评审通过后使用受管标签关系增量接口：仅 add/remove 已确认由系统管理的标签关系，在单个原生事务内完成；不得调用旧整组替换接口，不得按 50 个 ID 拆批。
6. 旧 PUT /api/v1/knowledge/tags 的 50+ 整组替换必须直接拒绝，不能拆分、不能假装 CAS 已控制。
7. 标签读取失败必须报错，不得当空数组；这是硬约束。

## 9. 业务模块与查询

### 9.1 文档工作台

同库查询原生文档 + ext_ 生命周期 + 版本族 + 附件 + 反馈 + 修订 + 审计。所有查询必须：

- 带 tenant_id、knowledge_base_id、document_id；
- 通过 NativeReader/GovernanceReader 的显式方法；
- 在返回前做 Core 权限检查或 Host 权限映射；
- 不把 UI 徽标当事实源。

### 9.2 阅读中心

保留 v1.1 设计：原件、解析、附件、版本、双窗对照、证据定位。单库只减少数据聚合成本，不改变：

- 历史阅读不等于现行问答证据资格；
- 预览权限不等于下载权限；
- 历史版本不得冒充当前版本；
- 未过门禁文档不得进入 RAG。

### 9.3 附件和修订

附件业务关系、元数据、回执、删除意图进入 ext_ 表；原始文件仍在原生文件存储。修订发布继续 Saga，不因同库改成非幂等直接写入。

### 9.4 查询性能

- P3 先做同库原生/扩展 join 的基准查询。
- 热查询使用 tenant_id_num 生成列或显式 CAST；对 lifecycle_current、lineage_edge、attachment_links 优先建索引。
- 禁止在 handler 中直接拼 SQL；所有 SQL 在 query 包并有单元测试。
- 任何新 query 必须提供 query plan 和 P95 基线。

## 10. 一致性设计

### 10.1 五条不变量

A. 生命周期 event/current/outbox 同事务；last_event_id 外键和 007 触发器不得绕过。
B. 治理操作与 governance audit 同事务；禁止先改状态再异步补审计。
C. 修订发布 Saga：意图 -> 远端检查 -> 创建/绑定 -> 哈希确认 -> 索引检查 -> 发布 -> 旧件失效；未知先对账。
D. supersedes/supplements/amends/interprets 关键关系同事务；可重建语义走 Outbox。
E. 标签、徽标、列表统计、图缓存都是派生数据，不是事实源。

### 10.2 跨域事务

| 操作 | 事务边界 |
|---|---|
| Host 生命周期事件 | Host ext 表事务 |
| Core 原生标签写入（仅 P4 可选） | Core 原生表事务；受管关系增量，不提供整组替换 |
| TagGov 写标签 | 首批停止治理标签投影后不再写；P4 如恢复，Core 受管关系事务 + Host 失败/回执记录（Saga） |
| 修订发布 | Host 意图 + Core 文档 Saga + Host 发布回执 |
| 附件删除 | Host 删除意图 + Core 原生删除 + Host 清理回执 |

禁止声称上述是跨进程全局 ACID。

### 10.3 锁和重试

- Host writer 使用 BEGIN IMMEDIATE。
- busy_timeout=5000；超过后返回可识别 BUSY，不得无限重试。
- 事务内不执行 HTTP、LLM、解析、长文件操作。
- 失败写 ext_outbox 或 ext_projection_failures；死信可重试但不得自动复活已耗尽任务。
- Core/Host 同时写时优先保证短事务；大批量迁移必须停写。

## 11. 迁移方案

### 11.1 前置检查

1. git status --short、git diff --stat、HEAD、BASELINE.txt。
2. 确认 Core/Host 全部停止，无后台 Worker。
3. 确认 DB_PATH、AGENTRAG_EXT_DB、实际打开的 SQLite 文件 identity。
4. 读取原生 schema_migrations 版本=51、dirty=0。
5. 读取扩展 ext_schema_migrations 版本=41、checksum 完整。
6. 检查 WAL/SHM、磁盘空间、文件权限。
7. 记录表数、行数、索引、触发器、外键、sqlite_sequence。
8. 用带真实 FTS5/sqlite-vec 索引的生产库副本生成 native object manifest：普通表、索引、触发器、视图、FTS5 虚表及影子表、vec0 虚表及影子表、schema_migrations、sqlite_sequence、sqlite_stat1；记录 name、type、SQL hash。对象清单不是固定 81 张表的替代。

### 11.2 备份

备份目录：

~~~text
migration-backup/
  weknora.db
  agentrag_ext.db
  launcher-config.json
  file-storage/
  encryption-keys/
  manifest.json
  integrity-report.json
~~~

使用 SQLite Backup API 或停写后的完整文件复制；不得复制正在写入的 DB。记录文件哈希和表计数。

### 11.3 目标库构建

推荐流程：

1. 停写并 checkpoint 两个源库。
2. 用 SQLite Backup API 复制 weknora.db 到目标。
3. 在目标上运行原生迁移检查，确保 version=51、dirty=0。
4. 用 Host 的 shared 模式迁移器在目标创建 ext_ 表；ext_schema_migrations 达到 41。
5. ATTACH 源 agentrag_ext.db 为 ext_source。
6. 按外键拓扑顺序复制扩展数据；复制 sqlite_sequence；保留 event_id、event.sequence、回执 ID。
7. 创建索引、触发器和视图；执行 007 触发器重放检查。
8. 复制 ext_schema_migrations 记录；校验 checksum。
9. 执行 PRAGMA integrity_check 和 foreign_key_check。
10. 生成 migration-report.json 和 integrity-report.json。

迁移工具必须是独立命令，不依赖 Core 在线服务；失败中止并保留现场。

### 11.4 核验项目

| 项目 | 标准 |
|---|---|
| 原生对象 | 与真实副本生成的 object manifest 一致；81 张业务表只是其中一部分，另含 FTS5/vec0 虚表及影子表、索引、触发器、视图 |
| 扩展表数 | 首个原型 91 张（90 张业务表 + ext_schema_migrations）；P4 应用 042-044 后才为 94 张 |
| 每表行数 | 与源库一致 |
| 主键/唯一键 | 无重复、无丢失 |
| 关键业务哈希 | event、current、outbox、附件回执、版本族发布头一致 |
| 索引/触发器/视图 | 完整 |
| 外键 | foreign_key_check 无输出 |
| 迁移历史 | schema_migrations=51；ext_schema_migrations=41；无 gap |
| 序列 | ext_lifecycle_events.sequence 连续 |
| 完整性 | integrity_check=ok |
| 权限 | Host 只读连接无法写原生表；写入测试使用专用 writer |

### 11.5 配置切换

生产环境：

~~~text
DB_PATH=/home/ybochuan/.local/share/agentrag/weknora.db
AGENTRAG_STORAGE_MODE=shared
AGENTRAG_EXT_DB=/home/ybochuan/.local/share/agentrag/weknora.db
~~~

兼容规则：

- 未设置 AGENTRAG_STORAGE_MODE，或明确设为 independent 时，保持现有双库行为；AGENTRAG_EXT_DB 必须是独立路径，launcher 继续拒绝与 DB_PATH 相同或 weknora.db 文件名。
- shared 模式下，AGENTRAG_EXT_DB 可省略；若设置，必须与 DB_PATH 的规范化绝对路径相同，否则 launcher 和 Host 都拒绝启动。
- Host 在 shared 模式下设置 DBPath=DB_PATH、NativeDBPath=DB_PATH；不得再回退到 data/agentrag_ext.db，也不得存在第三个数据库路径。
- launcher_config.py 只在 shared 分支放行同路径；strict 分支的 original 拒绝逻辑保留，避免测试和独立部署误用共享库。

启动顺序：

~~~text
路径 identity 检查
  -> 原生 schema 51/dirty=0
  -> 扩展 schema 41
  -> integrity_check / foreign_key_check
  -> Core Ready
  -> Host Ready
  -> Bridge 健康检查
  -> 开放业务流量
~~~

两套迁移不能并行执行。launcher 必须在 Core 启动前检查 DB_PATH；在 Host 启动前再次检查。

### 11.6 回滚

回滚触发：

- 行数/哈希不一致；
- foreign_key_check 异常；
- Core 或 Host 频繁 BUSY；
- 生命周期/标签/附件/RAG 门禁失败；
- 原生文档数量异常。

回滚必须区分“首笔真实业务写入前”和“首笔真实业务写入后”，不能只恢复迁移前双库：

**A. 首笔真实业务写入前（仅迁移/演练/只读验证）**

1. 停止 Core 和 Host。
2. 保存共享库现场和日志。
3. 恢复迁移前 weknora.db 和 agentrag_ext.db 的完整快照。
4. 恢复旧 launcher 配置和旧 independent 模式。
5. 启动双库版本并执行回滚验收。

**B. 首笔真实业务写入后（已产生文档、标签修改或治理回执）**

1. 立即停止 Core 和 Host、停止 Bridge 和后台 Worker，冻结新写入；记录切换后所有写入的起始时间和在途请求。
2. 对当前共享库做一次新的完整快照（不是迁移前快照），校验 integrity_check 和文件哈希。
3. 从该当前快照拆回双库：原生表导出为新的 weknora.db，ext_ 表导出为新的 agentrag_ext.db；保留 schema_migrations=51、ext_schema_migrations=41 及真实 FTS5/vec0 对象。
4. 对账：文档/原件、标签修改、生命周期、附件、修订发布回执、Outbox 在途项；无法对账的在途发布进入人工处理清单，不得假装已回滚。
5. 用拆回后的双库启动旧 independent 模式，执行回滚验收。
6. 将完整快照、拆回脚本、对账报告和演练记录归档。

**上线门槛：** 拆回演练必须在隔离环境至少成功一次，并覆盖“有在途修订发布”和“有生命周期/标签写入”两种场景；未演练不得切换。旧 agentrag_ext.db 保留只读，不立即删除。

### 13.3 治理与 RAG

GOV-01 至 GOV-12 沿用 v1.0 场景，但增加：

- 六态生命周期按记录验证，现有 active -> superseded/archived 转换不被首批改变；

- 标签读取失败报错，不当空数组；50+ 整组替换拒绝而不是拆批；
- 附件父文档失效后附件不能绕过门禁。

RAG：

- active 可检索；
- scheduled 不提前；
- stale/superseded/archived 不作为普通证据；
- 治理服务不可用时不放行；

## 15. 风险与回滚

| 编号 | 风险 | 等级 | 应对 |
|---|---|---|---|
| R-01 | 迁移丢数据 | 极高 | 离线备份、行数/哈希、回滚演练 |
| R-02 | 原生/扩展 schema 冲突 | 高 | 表名前缀、双迁移目录、release manifest |
| R-03 | 单文件写锁竞争 | 高 | 短事务、busy_timeout、混合负载测试、保留双库回退 |
| R-04 | 上游升级冲突 | 高 | 核心补丁清单、PATCHES、上游迁移回归 |
| R-05 | 标签整组替换/50 ID 限制 | 高 | 首批退出 gov 投影、读事实；50+ 整组替换直接拒绝、禁止拆批；不宣称 CAS 已控制旧接口 |
| R-06 | Outbox 重复/死信 | 中高 | 幂等键、租约、RetryBlocked、对账 |
| R-07 | 附件归属错误 | 高 | SHA-256、父子版本、回执 |
| R-08 | RAG 门禁退化 | 极高 | fail-closed、Gold Set、误放行=0 |
| R-09 | Core patch 影响原生 | 高 | 首批仅 CP-01/02；定向测试、逐项 PATCHES |
| R-10 | 回滚丢共享库新数据 | 极高 | 首笔写入前恢复快照；写入后从当前共享库快照拆回双库并对账；拆回演练作为上线门槛 |

回滚原则：不能只恢复迁移前双库；必须按“首笔真实写入前恢复旧快照、写入后从当前共享库快照拆回双库并对账”执行，且拆回演练通过。
